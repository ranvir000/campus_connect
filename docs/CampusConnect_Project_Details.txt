1. Abstract
CampusConnect is a role-based web portal that brings a college student's day-to-day information into one
organised website. Students sign in to view their subjects, weekly timetable, assignments, department
notices, club events, campus resources and to raise support requests whose status they can track. An
administrator (Head of Department) signs in to a separate console to publish and manage notices, events
and resources, and to review and resolve student requests. Both portals read and write the same live
database, so every change made by the administrator is visible to students immediately and every student
action (event registration, support request, assignment submission) is visible to the administrator.
The system is built with a React + TypeScript single-page frontend, a Python FastAPI REST backend and
a MongoDB database, with cookie-based session authentication, server-side validation and an automated
test suite.
2. Introduction & Problem Statement
In most colleges, student information is scattered: notices are pinned on physical boards or forwarded as
PDFs on messaging groups, timetables are shared as images, event registrations happen on separate
forms, and complaints are raised verbally or on paper with no way to track them. Students miss deadlines
and announcements, and the department has no single place to publish information or see what students
need.
Problem: There is no single, organised, always-available platform where students can access academic
and campus information and where the department can publish and manage that information.
Solution: CampusConnect — a centralised, responsive web portal with separate student and
administrator roles, backed by a shared database so information stays consistent for everyone.
3. Objectives
  Provide a single portal for academics, notices, events, resources and student support.
 Implement secure login with two roles — Student and Administrator — with role-based access to pages
and APIs.
 Give students a dashboard summarising today's classes, pending assignments, latest notices and
upcoming events.
 Allow the administrator to create, edit, publish/unpublish and delete notices, events and resources
(CRUD).
 Provide a support/grievance system where students raise requests and track status (Pending → In
review → Resolved).
 Keep data synchronised in real time between the student and administrator portals through one
database.
 Build a responsive, accessible interface that works on desktop and mobile, including a dark mode.
 Validate all inputs on both client and server and verify the system with automated tests.

10. Security & Validation
  Password hashing: PBKDF2-HMAC-SHA256 with a random 16-byte salt and 100,000 iterations;
constant-time comparison.
 Sessions: random 256-bit token in an HTTP-only, SameSite=Lax cookie (not readable by JavaScript),
valid 7 days, removed on logout.
 Role-based access control: server-side dependencies require_user and require_admin;
unauthenticated requests get 401, students calling admin APIs get 403. The frontend also guards
routes (students are redirected away from /admin).
 Input validation: Pydantic models enforce required fields, maximum lengths, allowed values (ticket
status, priority) and numeric ranges (event capacity); invalid data returns 422. Forms disable submit
until required fields are filled.
 Business rules: no registration for past or full events; unique registration per student per event; only
pending assignments can be submitted; students see only their own support tickets; drafts are never
exposed to students.
 Safe search: search text is regex-escaped before querying the database.

11.1 Login
User opens /login → selects Student or Administrator → submits e-mail and password → server verifies
the hash → creates a session and sets the cookie → frontend clears any old cached data and redirects to
/dashboard (student) or /admin (admin).
11.2 Support request lifecycle
  Student submits form --> ticket created (status: pending, timeline: "Request received")
        |
  Admin opens ticket in Helpdesk --> sets "In review" + note --> timeline entry added
        |
  Admin sets "Resolved" + note --> student sees resolved badge and the note
11.3 Notice publishing
Admin creates a notice (published or draft) → it is stored with author and IST timestamp → published
notices appear instantly for students with search and category filtering → admin may later edit, unpublish
or delete it.
11.4 Event registration
Student opens Events → clicks Register on an upcoming event → server checks the event exists, is not in
the past and is not full → registration saved → count updates for the student and in the admin events
table. Cancel removes it.

12.1 Bug found and fixed during testing
Testing revealed that creating a new event stored computed display fields in the database, which caused
the events list to fail with a server error. The fix stores only real event fields and recomputes per-viewer
values (registered, count, past) on every request; the regression tests now pass.

15. Deployment
  Source code hosted on GitHub.
 Database: MongoDB Atlas (free M0 cluster) — connection string supplied as the MONGO_URL
environment variable.
 Backend: Render Web Service — pip install -r requirements.txt, start uvicorn
server:app --host 0.0.0.0 --port $PORT.
 Frontend: Render Static Site — yarn build, publish dist; /api/* is rewritten to the backend so
login cookies remain same-origin.
 On first launch the backend creates the demo accounts and sample data automatically.

17. Advantages & Limitations
Advantages
  Single source of truth — no outdated copies of notices or timetables.
 Role-based security on both server and client.
 Responsive design usable on phones; dark mode for comfort.
 Transparent grievance handling with a full status timeline.
 Modular code (separate routers, models and pages) that is easy to extend.

19. Conclusion
CampusConnect meets its objective of providing one organised portal for students and the department. It
implements secure role-based authentication, complete CRUD management for the administrator,
real-time consistency between the student and administrator views through a shared database, input
validation and business rules on the server, and a responsive interface. Automated backend and browser
testing confirmed that all major workflows function correctly.
